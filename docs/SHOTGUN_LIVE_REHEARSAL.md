# Bounded Shotgun Live Test Lab

The Lab is a command-line operator workflow. It uses the installed production checkout builder, browser transport, strict scheduler, permits, journals, independent provider verifier and official QR recovery. Ordinary Available Now still refuses `SHOTGUN_IMMEDIATE_BURST_BLOCKED`. The Lab does not edit saved production plans, fingerprints or release offsets.

Start with one exact target in a local `request.json`:

```json
{"kind":"SHOTGUN_LIVE_REHEARSAL","date":"2026-11-04","wing":"MANGO","court":1,"worker":"A","start":"08:00","duration":1,"maximum":600,"attempts":1,"payment":false}
```

This is a format example, not a selected or currently available target. Choose the actual date, court, hours, browser and ceiling deliberately. Execution independently observes current published availability and rates, prepares genuine security, then observes availability again. It refuses a changed plan. Freshness is checked again at the final POST gate using monotonic elapsed time. An outstanding or UNKNOWN overlapping interval remains blocked across profiles regardless of advertised expiry.

Author the short-lived exact-target authorization from the owner's actual directive, using the canonical installation root:

```text
.local/runtime/node.exe --import tsx Source/scripts/authorize-shotgun-live.ts --authorize .local/shotgun-rehearsal/<unique-run> <request.json> <owner-directive.txt> --attest-owner-scope
```

This writes authorization only; it performs no browser operation or booking. It records the directive hash, exact-request fingerprint, explicit no-payment/no-cancellation/no-retry attestation, installed SHA and production module hashes. It does not infer approval from a file merely existing. The invoking operator must have the owner's authority. Authorization lasts at most 15 minutes, must remain valid after preparation and at the final POST, and does not replace the write-once execution claim or consumed production permit. Existing authorization files are never overwritten.

The updated Lab requires `SHOTGUN_LIVE_LAB_ENGINE_VERSION=2` in the canonical installed dispatcher. Source changes alone cannot qualify or substitute for that installation. Integrity detection and all execution locks still apply.

Run from the canonical installation root, using the existing installed runtime:

    .local/runtime/node.exe --import tsx Source/scripts/rehearse-shotgun-live.ts --execute .local/shotgun-rehearsal/<owner-approved-run>

The directory must contain the explicit `shotgun-live-authorization/v2` authorization created above. Execution is claimed write-once before arming. No authorization is inferred from this document or generated by the executor itself. Ctrl+C requests Stop; the final transport gate also checks it. No hidden follow-up booking run is scheduled.

Each target accepts 1-3 hours, at most PHP1,800, one POST, and no payment. It requires a clean/expired browser state, no execution lock, fresh published availability/rates, a valid existing customer binding, an unused production journal target and a GOOD fresh network clock. It never clears retained locks, recycles journals, retries checkout, adds fallback targets or changes the normal immediate-burst refusal.

After a single-shot run on the same installed engine has independently confirmed the hold and reached both original-tab and fresh-tab QR, an independent-target Lab request may use `{"kind":"SHOTGUN_LIVE_LAB","requests":[<target-A>,<target-B>,<target-C>],"attempts":3,"payment":false}`. Select one to three entries; the budget must equal the count. Every entry uses the single-target schema above. Workers and courts must be distinct, dates equal, customer/profile identities independently eligible, and all targets nonconflicting. Add `--single-shot-run <successful-run-name>` to the authoring command for a multi-target run. Both author and executor verify the hash-bound prior live result, its exact installed SHA/module hashes and both genuine QR outcomes. Intercepted/simulated results cannot qualify it. This prerequisite establishes permission to test a small independent topology, not repeatability or release qualification.

The targets share a future rehearsal anchor and a single production frozen race. Each has its own one-shot permit and journal. Provisional evidence reserves court/wing safety capacity without counting as confirmed achievement. Conflicting and over-budget follow-ups stop; authorized independent targets can continue within the quota. UNKNOWN, throttle and payment signals retain race-wide conservative suppression. Arbitrary same-target density belongs to offline simulation, not this live workflow. A retained global lock blocks the entire Lab; another identity is never used to evade it.

`prepared-plan.json`, `execution-claimed.json`, `result.json` and `exit-evidence.json` separate source/installed provenance, authorized budget, observed booking POSTs, worker results, local response validation, provider confirmation, both QR paths, clock domains, recovery milestones and lock retention. Reports are local. Browser/customer secrets, checkout capabilities and QR payloads remain in their existing private stores. A transport failure without an observed POST remains uncertain; an absent request observation alone is not proof of an unsent request. Original journals and claims stay authoritative.

The source wrapper calls the canonical installed freezePrecisionRace, armPrecisionRace and dispatchArmedPrecisionRace functions with SHOTGUN_STRICT. A future trigger is labelled as a rehearsal anchor, never as the official release. The result includes installed module hashes, strict dispatch state and safe observations. A validated hold retains the production lock and must pass both the initial official QR handoff and restoration from the saved private response in a fresh tab. Tokens and private responses are not printed.

Genuine security preparation completes before the rehearsal anchor is chosen and before any target journal is armed. The clean venue page is loaded fresh, matching production preparation; selected/held pages are not discarded. The browser is surfaced first; a visible human-verification prompt is surfaced again without being solved automatically. Preparation failure stops before arming. Published cells/rates and the trusted clock are checked again after preparation. The context must be at most 15 seconds old before freezing, arming and the dispatcher prewarm callback. Prewarm reuses that same context instead of starting another challenge against a countdown. The test anchor is eight seconds ahead after these checks; the actual scheduled 08:00 release deadline is never moved or relaxed.

For genuine security preparation alone, with both booking routes blocked and no reservation permit, authorization claim, armer or dispatcher invoked:

    .local/runtime/node.exe --import tsx Source/scripts/check-shotgun-rehearsal-security.ts B

This discards the acquired context when the check process ends. A successful security-only check is not a live booking, recovery test or release-readiness guarantee.

The November 1 [incident and rehearsal report](incidents/2026-11-01-release/README.md) records the initial unsent rehearsal and the subsequent one-attempt verified hold. The latter exposed a canvas-only installed QR wait; source recovery and both production handoff paths now accept the explicit `Payment QR code` image as well as a canvas, with exact order-summary checks unchanged. Installed module hashes must be checked independently: a source fix does not replace the modules this CLI imports from the canonical installation.

A rehearsal is not a complete recreation of 08:00 contention, multi-attempt fan-out, priority/observer topology or the saved production preparation lead. One successful attempt does not establish full release readiness. An unsent failure is not automatically retried. Pending/unknown submissions retain their authoritative journal status.
