## Scope and existing findings

The authorization and required specific-attempt approval are in the supplied assessment task. `HEADERLESS_CHECKOUT_INVESTIGATION.md` established only that a valid body can be constructed without the two headers; it did not test server behavior. `API_FIRST_IMPLEMENTATION_REPORT.md` records the existing read-only API path, fresh-proof and response validators, disabled live submission gate, and unsupported checkout restoration. Those findings are unchanged.

The existing `OndaBrowserSessionTransport` and desktop browser/hybrid methods were not edited. The new `headerless-assessment.ts` and `headerless-assessment-transport.ts` form a separate callable boundary with no CLI or desktop wiring. They require an exact approved facility, space, date, two consecutive hours, client ID, customer ID, price ceiling and approval reference. The entry point requires an availability snapshot captured within 15 seconds and containing both matching available hours at the planned prices. The existing two-hour adapter then obtains a fresh proof for each hour, builds the observed checkout body, claims a durable one-shot permit and validates any pending response. The assessment transport alone omits the two named verification headers. It retains same-origin browser credentials, JSON content type, redirect rejection and no-cache behavior.

Both `ONDA_HEADERLESS_ASSESSMENT=APPROVED_ONE_SHOT` and the existing `ONDA_EXPERIMENTAL_TWO_HOUR_SUBMIT=SUPERVISED_ONE_SHOT` gate are required. A dispatched rejection, timeout, malformed result or lost session leaves the journal in `unknown` and forbids automatic checkout retry. The callback receives only status, coarse response shape and a challenge-text hint; no request body, response body, proof, token, fingerprint, cookie or customer information is logged by the harness.

## Hold release and operator reconciliation findings

The same [checkout service bundle](https://app.onda.fit/_next/static/immutable/chunks/1y9e760opu2ka.js) defines `releaseBookingCheckout`: `POST /api/bookings/public-checkout/{bookingId}/release`, with a checkout access header when `checkoutToken` exists. The [public booking UI](https://app.onda.fit/_next/static/immutable/chunks/1vw2uo7rgshl5.js) calls it when a user changes selection from a pending checkout, and refuses to clear checkout state if release reports failure. This is an **observed public UI action and source contract**, not a tested release procedure for an API-created reservation. No release request was sent. A successful checkout response may include `checkoutToken` on a booking; the UI extracts it. The current experimental adapter returns booking IDs, session ID, transaction ID and expiry but does not retain a checkout token or perform release. The server's token requirement, group-release semantics and availability restoration have not been verified.

Onda's [public operator page](https://onda.fit/) says staff can view/manage bookings and see paid, pending and on-site payment states. It does not document the exact controls for locating a pending booking, linking its transaction, cancelling it, or confirming that a two-hour hold has disappeared. No authenticated Thirsty Pickle operator session or SOP was available in this checkout; when asked for one, the user answered “no.” The [player-app listing](https://play.google.com/store/apps/details?id=com.onda.fit) mentions cancelling sessions from the Bookings tab, but that does not establish an operator procedure for an unpaid API-created hold. No real booking was touched.

The observed pending response carries two booking IDs and numbers, one session ID, a transaction ID, transaction reference equal to the first booking number, common hold expiry, exact court/date/hour fields and customer ID. If the response arrives, these fields can be compared with a staff booking and transaction view. The public site also has a [booking-by-ID read service](https://app.onda.fit/_next/static/immutable/chunks/35vw98cw658m8.js), and its UI resumes checkout only when that result says `canResumeCheckout`. **That lookup requires a booking ID**, so it cannot resolve a timeout that returned no ID. Source code is not proof of an authorized, authoritative lookup by logical booking key.

For an ambiguous POST, the local journal must remain `unknown`. The operator needs an authenticated search by the exact facility, court, date, two hours, dedicated test customer, attempt time and PHP amount; then inspect all matching booking records, their session, status, hold expiry, booking numbers and linked transaction before declaring created or absent. A single empty availability grid is not sufficient to prove absence because another party could have booked the slot. The operator must also confirm whether a pending hold can be released and then verify both hours are available again through the operator schedule and a fresh read-only availability response. The actual operator search/filter fields, transaction linkage and release controls remain **NOT OBSERVED**. There will be no second checkout POST while this is unresolved.
