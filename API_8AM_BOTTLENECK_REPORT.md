# Thirsty Pickle release bottleneck review — September 17, 2026

## What the current Chrome path waits for

The release refresh uses `page.reload({ waitUntil: 'commit' })`; it does **not** wait for full navigation. It then waits for the venue heading and date picker to attach, become visible, and the picker to become enabled (`waitForBookingShellForRelease`). After clicking the released date, `clickReleasedTargetDate` waits for the target heading and `waitForGrid`. The grid barrier requires one grid, no `aria-busy`, all 16 target-date rows, and seven slot cells per row. `snapshot` and `validateSnapshot` then enforce 112 well-formed cells before the preference is resolved. The availability API response is not the blocking dependency in this path; rendered grid readiness is.

The historical September 11 8 AM log `a9c37b00-9f63-4451-ad3c-a7186120e221.json` recorded reload commit at +335 ms and shell ready at +18,518 ms relative to release trigger, an 18,183 ms shell delay. The target was clicked at +19,415 ms, then the run failed before `targetGridReady`. That log cannot separate server response, JavaScript hydration, and date-picker enablement within the shell delay. Another release log `b52e5ded-2743-4a0a-ac12-57a17dcedbe3.json` recorded shell ready at +1,264 ms, target grid ready at +1,591 ms, preference resolved at +1,603 ms, and Proceed clicked at +2,774 ms. It had an API request start but no successful API response, so the candidate source was UI only. The user has separately observed very slow grids at two busy releases; these are treated as a recurring operational bottleneck, not dismissed because one historical log was faster.

## API versus visual grid

An off-peak **read-only** GET for already-released September 19 returned in 262 ms. Validation took 3 ms and exhaustive two-hour planning took 194 ms. The sampled 12:00 two-hour preference had no consecutive availability. This confirms the availability provider and planner can run without the grid, but it does not predict an 8 AM response or establish a bookable candidate.

An offline simulated release held the target grid unrendered for 250 ms after the API candidate was ready. The test observed `availabilityApiCandidatesReady` before `targetGridReady`; hybrid did not reach `preferenceResolved` or a slot click until the grid was released. The API-first experimental planner has no DOM grid dependency. It can choose a candidate before visual rendering, then obtain two fresh hour proofs and submit one two-item checkout only after legitimate verification is available.

The existing hybrid implementation starts the API GET at release and precomputes candidate preferences when it returns. Yet `observeRelease` awaits `clickReleasedTargetDate`, which awaits `waitForGrid`, before calling `discovery.rank` and `resolvePreference`. Hybrid therefore cannot select or proceed independently of grid readiness. It remains a possible fallback/diagnostic path, not the primary solution to this bottleneck.
